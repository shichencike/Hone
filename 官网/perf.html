#性能基准：Hone vs Python vs Rust

9 个维度、三语言等价实现、同机实测。所有脚本源码见仓库 bench/ 目录（bench.sh 一键复现）。

测量方法

  • 每项均为单次运行耗时（毫秒，越小越快）；结果值三语言完全一致（交叉校验通过）。
  • 三语言脚本逐项等价：同一算法、同一工作量、确定性输入；源码见 bench/*.hn、bench/py/、bench/rs/。
  • Rust 二进制先运行一次预热（避开杀毒软件对新 exe 的首扫干扰，实测首扫附加约 3.8s），取稳定运行时间。
  • Hone 列表为值类型：append 与 a[i] = x 均按拷贝语义实现， 故 list_append（构建 2 万元素）与 sort（冒泡 1000）对 Hone 为 O(n²) 负载，耗时显著偏高。
  • 本机为 1GHz 低功耗 CPU，绝对数值偏大；相对比例更具参考意义。

要点解读

  • 计算类负载：Hone 约为 CPython 的 1.8~6.4 倍耗时（fib 4.6x / 纯循环 3.2~3.6x / 浮点 5.3x / 字典 6.4x）， 与 README 公布的优化后基准一致（fib(26) ≈2.1s、2000 万循环 ≈42s、字符串拼接 20 万 ≈19s）。
  • 集合值类型语义：Hone 的列表按值拷贝（append、a[i]=x 均产生新列表）， 构建/排序类负载为 O(n²)，比 Python 慢 160x+；若后续改为写时共享（copy-on-write）可大幅改善。
  • Rust：计算本身几乎瞬时，本机测得 ~250ms 主要为进程启动/杀软扫描开销（空程序同为 248ms）。
  • 结论：Hone 作为轻量脚本语言，计算性能处于 CPython 同级（略慢 2~6 倍）、远低于原生 Rust（数十到数百倍）； 开箱即用的代价换取零依赖单文件部署。性能热点场景建议用 hone prof 定位后改用 C 扩展（hone build --dll）或内联到 Rust。

AOT 原生编译（hone build --exe -c）

把脚本编译为 C 中间文件、再交给系统 C 编译器产出原生可执行文件。 实测相对解释器有接近一个数量级的稳定加速（MinGW-w64 gcc 16.2.0， 预热后取多轮最快值）：

基准AOT解释器加速比
递归 fib(26)267 ms2,530 ms9.5x
循环累加 200 万次514 ms6,203 ms12.1x

产物体积约 58.6 KB，零运行时依赖。

性能短板的如实说明

  • 并非「接近 C 的性能」：等价的 rustc -O 跑 2000 万次循环约 274 ms， AOT 版约 2,962 ms——慢约 10 倍。
  • 原因是 AOT 生成的 C 对每次整数运算都做装箱（hn_int()）、 深拷贝（hn_copy()）与释放：以递归 fib 为例，生成的代码形如 hn_truthy(hn_le_v(hn_copy(v0), hn_int(1)))， gcc 无法将其优化成寄存器运算。
  • 这是「列表/字典值语义 + 统一装箱 HnValue」的必然代价， 调高优化级别（-O3）无效——不是编译参数问题。
  • AOT 的真实定位：比解释器快一个数量级、几十 KB、零依赖的分发方案。 对 I/O、脚本编排类负载影响可忽略；纯计算密集的热循环仍建议用 hone prof 定位后改用 C 扩展（hone build --dll）。

复现方式：bash bench/bench.sh（编译 Rust 基准并运行三语言各 3 次取最快，输出表格）。
