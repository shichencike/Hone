测量方法

  • 每项为子进程 wall time（毫秒）：默认 3 次运行取最快，单次超过 5 秒的负载只跑 1 次（解释器慢负载）； 含解释器 / 运行时启动开销，小负载（str_replace 等）受启动成本影响明显。
  • 三语言脚本逐项等价：同一算法、同一工作量、确定性输入；源码见 bench/*.hn、 bench/py/、bench/lua/。
  • 双引擎口径：interp = hone 脚本.hn（AST 解释器）； VM = hone 脚本.hn --vm（寄存器式字节码）。
  • Hone 列表为值类型：append 与 a[i] = x 均按拷贝语义实现， 故 list_append（构建 2 万元素）与 sort（冒泡 1000）对解释器为 O(n²) 负载，耗时显著偏高。
  • Runner 规格随 GitHub 托管池浮动，绝对数值每次运行可能有小幅波动；相对比例更具参考意义。

要点解读

  • 引擎对比：VM 通常快于 interp，解释器约为 CPython 的 2~6 倍耗时（视负载）。
  • 集合值类型语义：Hone 的列表按值拷贝（append、a[i]=x 均产生新列表）， 构建/排序类负载对解释器/VM 为 O(n²)。
  • Lua 5.4：寄存器 VM + 高效字符串内化，纯循环 / 字符串类负载通常强于 CPython； 字符串拼接（s = s .. "abc" 整串重建）语义与 Python 相同，同为 O(n²)。
  • 结论：性能热点场景先 hone prof 定位， 必要时改用 C 扩展（load + typed FFI）。
